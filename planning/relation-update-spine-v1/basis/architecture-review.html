Cellerator: architecture, execution, and biological optimization review

Review date: 5 September 2026
Purpose: Find the architecture and algorithms most likely to make biological computation exceptionally fast.
Method: Read-only investigation of live source through Project Control, examination of retained performance artifacts, and primary-source research. No repository, API, build, Todo, or implementation changes were made. No benchmark or test was executed for this review.

1. Executive synthesis

What Cellerator currently is

Cellerator is currently a substantial, unevenly integrated biological execution research system, with a more executable native computation layer than its installed compiler/libCellerator product exposes. Its strongest technical center is not the source-language parser. It is the combination of persistent biological identity, structure/value separation, exact support accounting, physical projection, prepared execution, and operation-specific kernels. [S01–S02, S11–S26]

There are several distinct realities:

  • The installed target named libCellerator contains the passthrough-driver and tooling-architecture implementation units, not the native math engine. The installed cellerator entry point forwards to another compiler. Compiler component targets such as Frontend, Planning, and Realization are INTERFACE boundaries in the inspected configuration. [S01–S03]
  • Independently, the repository contains real parser/AST/semantic/profile/IR/backend algorithms, including actual external object compilation and narrow generated PTX. Some “vertical slices” are deliberately small demonstrations with scalar/reference execution, not the complete route implied by their names. [S04–S10]
  • The native build contains real sparse, feature-major, WMMA, residual, contraction, segment, normalization, update, fusion, training, and sequence-predicate execution paths. Some are directly callable through typed APIs; fewer are connected through the same generic candidate/preparation route. [S11–S25]
  • Retained performance evidence establishes particular mechanisms on particular fixtures. It does not establish Cellerator-wide superiority or a broad biological speedup. The newer operation portfolio's reviewed readiness receipt explicitly does not claim CUDA runtime timing or biological promotion. [S26]

The strongest assets

The separation of structure identity, structure epoch, value generation, logical edge order, and persistent physical order can enable optimizations a conventional “call SpMM on this CSR” interface cannot express conveniently. These contracts already support useful reuse in native execution. The older N16 training path reuses forward/transpose structure and updates values in physical order; the sequence integration caches predicate-derived artifacts across repeated state computations. These are concrete assets, not merely future intentions. [S12, S15, S24–S25]

Exact heterogeneous support coverage is another asset. It allows sparse and dense fragments to coexist without silently discarding inconvenient biology. The geometry system also already has sparse incremental greedy machinery and support-derived grouping strategies. The planner already has dynamic programming over chains, preparation/reuse cost terms, measured-candidate hooks, and a separate two-dimensional cost/memory Pareto helper. These should be evaluated and connected, not rediscovered under new names. [S14, S16–S18]

The largest uncertainties

The largest uncertainty is not whether Cellerator can contain a language. It is whether the semantic and execution layers describe one coherent computation, and whether biological information changes that computation enough to justify the machinery.

Three questions dominate:

  1. Can both a native C++ caller and the source language reach the same correct, performant prepared execution from the same semantics?
  2. On realistic repeated biological workloads, which gains come from better kernels, which from layout/preparation reuse, and which specifically require biological meaning?
  3. Is the most useful compilation unit an individual operation, a composition, or a family of related biological computations with shared structure and bounded variation?

Recommended direction, with qualifications

Make a prepared biological-computation engine the shared architectural center. Offer immediate native math, prepared operations, and optional graph construction to C++ users; make the language another way to express that graph and its useful facts. Keep explicit expert access to planning, layouts, IR, candidate forcing, and backend code. Do not expand the language merely to complete a checklist, and do not discard it merely because its current integration is incomplete.

This is not a recommendation for permanently library-first or compiler-first development. It is a recommendation to make performance-producing semantics and execution primary. A compiler-visible composition can be valuable; it does not require that every caller adopt the language. Structural code generation or JIT may become important for stable biological families, but current evidence does not justify making it the next central implementation project.

The strongest longer-term hypothesis is that Cellerator should compile biological structure plus a workload family, rather than simply compile source text plus one matrix. This preserves the best existing ideas while opening genuinely biological optimizations: repeated regulatory support across states, sequence-derived invariant relations, exact factorized gates, hierarchical mechanisms, ancestry/edit sharing, and perturbation-driven incremental updates. Each requires explicit validity conditions and comparative experiments.

2. Current architecture map

2.1 Installed product versus repository implementation

The installed surface is currently approximately:

cellerator executable
  -> run_driver_passthrough_v1
  -> external compiler command

Cellerator::libCellerator
  -> passthrough-driver implementation
  -> celleratord architecture/routing validation

installed include/ + stdlib/ + profiles/
  != an installed, linked implementation of all exposed headers

cmake/compiler/CelleratorHostSdk.cmake:4–38 is decisive. It defines only the two implementation sources in the named library and exports the library plus the two tools. It installs stdlib/, not the new library/. Its generated package config reports compiler/runtime availability while reporting no CUDA backend. The root build reaches this host SDK before the CUDA-disabled early return; substantial native math targets lie beyond that return. Thus “host-only build works” is not equivalent to “native biological math is available on CPU.” [S01]

2.2 Compiler implementation islands

  -> source records and AST handles
  -> semantic type/effect/operation descriptions
  -> semantic IR and composition descriptions
  -> planning IR, profile identities, decomposition/atom imports
  -> selected-plan demonstrators
  -> realization descriptors and symbolic bindings
  -> host-reference prepared-program slice

separate backend paths:
  CSR-oriented CPU computation
  generated C++ -> external compiler -> ordinary object
  narrow generated PTX -> ptxas -> cubin

Important symbols include resolve_operation_kind, lower_selected_relation_plan_v1, execute_prepared_relation_slice_v1, profile-artifact build/validation functions, and external object/PTX assembly functions. The selected-relation realization slice records the selected candidate but constructs a host-reference callback regardless of that candidate's physical implementation. It is a real executable demonstration, but not evidence of end-to-end GPU candidate realization. [S05–S10]

The source-to-selected-plan demonstration requires exactly two semantic operations and selects between supplied alternatives. That is not the same algorithm as the native end-to-end planner. Likewise, the source-to-semantic demonstration has a separate lightweight parser and scalar interpretation. Multiple parallel representations are present; they are not all interchangeable instances of one pipeline. [S06–S08]

2.3 Native execution paths

C++ typed relation/state/support/axis views
  -> biological ABI + identity/lifetime validation
  -> operation core v1 or v2
  -> geometry acquisition / semantic geometry
  -> physical projections and value planes
  -> candidate discovery / direct typed provider access
  -> planner and preparation factory
  -> prepared operation or prepared program
  -> caller-owned buffers, stream, workspace, readiness events
  -> CUDA / vendor / host callback

This is not one universally connected path. The core-v1 builtin catalog, newer relation-algebra descriptors, provider-specific portfolios, typed launch APIs, training programs, and sequence integration are distinct entry routes. A user who knows the right internal/public headers can reach functionality that the named installed library does not expose coherently. [S11–S15, S19–S25]

The five builtin candidates are narrower than the complete native kernel inventory: row-masked N1, CSR fallback N1, feature-major widths 1–16, feature-major CTA widths 17–64, and a transpose backward N1 candidate. The newer algebra catalog includes operations that intentionally fail closed through the old preparation interface. This is preferable to silently wrong dispatch, but it leaves a real integration gap. [S13]

2.4 Permanent ownership of former campaign work

CE-GEO implementation now lives primarily under src/geometry/, src/compute/projection/, and src/compute/architecture/providers/nvidia/{common,sm70}/. CE-EXOP fan-in is explicitly in src/compute/CMakeLists.txt, with permanent provider and candidate sources for residual, apply, transpose, contraction, edge gradients, segment operations, and fusion. Campaign-labelled portfolio targets still aggregate these permanent implementations. [S11, S16, S19–S23]

JBC-related decomposition, atom, binding, and lowering-resumption sources are included by the cellerator_jbc_v1 aggregate. The inspected atom-fragment and resumption units validate coverage, identities, resource/cost fields, and stage compatibility. They are useful executable validators, not themselves code generators. The compiler planning IR can import decomposition alternatives and atom requirements. That connection is real, but does not prove a fully automatic decomposition-to-kernel path for every operation. 4. High-performance implementation inventory

4.1 Apply and dense fragments

The sm70 provider declares WMMA f16 × f16 with f32 accumulation. The N64 implementation really invokes WMMA and uses output-owned accumulation across relation tiles. Shared-A variants use small shared buffers; this is not evidence of Ampere-style asynchronous copy. Wider feature panels and alternative WMMA shapes are also actual launchable code, subject to their packed geometry and width contracts. [S19]

The older v100_dense_fragment_candidate.cu uses atomic accumulation. It remains useful as a benchmark/negative control and has standalone usage; it should not be labelled dead solely because newer output-owned paths exist. The retained data also shows that output ownership does not win at every depth. [S19, S26]

The PTX m8n8k4 experiment is an instruction-level probe, not a complete general relation implementation. A provider inventory should distinguish an instruction experiment from a prepared operation that accepts ordinary relation bindings.

Concrete integration problem: apply_inventory_v1.cc describes some N64 variants as pure-sparse, with launch/resource values inconsistent with the inspected WMMA kernel. A planner consuming stale metadata can make wrong decisions even when the kernel itself is correct. Generate or verify launch/resource metadata against the actual bound implementation, and retain an explicit “declaration only” state when the symbol is absent. [S13, S19]

4.2 Hybrid and residual execution

enqueue_relation_apply_hybrid_v1 performs value packing, MMA work, residual work, and an affine epilogue. Its local implementation validates fallback/cost fields but does not itself compare costs or invoke the supplied sparse fallback. Therefore a caller must make the decision; the existence of the fallback field does not make this function an automatic hybrid-versus-sparse optimizer. [S19]

Residual kernels include warp-per-row and high-degree variants. Some high-degree variants parallelize output features while each feature traverses all row edges serially. That can be reasonable for wide states and poor for narrow, high-degree rows. Degree alone is insufficient for scheduling; the relevant space is at least degree × width × source reuse × output ownership. [S19]

Two names overstate the degree of fusion if read casually. One same-owner residual kernel combines sparse traversal with an already materialized MMA contribution. Another fusion helper merely combines two materialized arrays. Neither is equivalent to retaining a Tensor Core accumulator while executing residual arithmetic in the same producer kernel. Both may still save useful work, but their actual stage boundaries must be visible to the planner. [S19, S23]

4.3 Contraction and gradients

Sparse contraction has meaningful thread-per-edge, warp-per-edge, and CTA-per-edge alternatives. The edge-value-gradient adapter correctly reuses this computation: an edge gradient is the dot product of source activation and destination gradient. This argues against inventing a separate arithmetic primitive solely because the biological role changes. [S20]

The rectangular contraction path genuinely computes dense score tiles through WMMA and adds a scalar tail. However, its request validator accepts dense_width >= 16 without enforcing the half-precision leading-dimension and alignment constraints used by load_matrix_sync. Width 17 is a concrete adversarial case: adding a scalar tail does not repair the invalid leading dimension of the WMMA prefix. The official CUDA contract requires a 256-bit aligned pointer and half leading dimensions that are multiples of eight. This is a source-confirmed precondition gap, not a runtime failure observed in this review. [S20; R08]

4.4 Segments, normalization, edges

Segment kernels implement substantive reduction behavior, including empty and nonfinite policies. Their CTA-per-segment/per-feature traversal should be tested for coalescing and degree imbalance rather than accepted as intrinsically optimal. Native normalization supports several modes and explicit edge cases, while the merge-state and demonstrator layers do not all share those same conventions. [S21]

Dynamic masks currently often operate by zeroing relation values. That is not interchangeable with excluding an edge from a reduction: 0 * NaN, normalization denominators, and sparse structural semantics can differ. Sparse axis updates require unique indices by caller promise; they are not a duplicate-index reduction engine. Some update kernels use 32-bit local counts and launch arithmetic; global 64-bit identity alone does not prove large-index safety. [S22]

4.5 Fusion and training

The most concerning algorithm is the fully fused sparse exchange. It recomputes the feature dot product while computing maxima, normalization sums, and weighted output, and repeats this for each output feature. For E edges, score width K, and value width V, this can turn an O(E(K+V)) composition into O(EKV) arithmetic. Fewer launches do not compensate automatically for this change in work. [S23]

The old native N16 training path, by contrast, is a genuinely connected implementation: forward relation application plus bias/ReLU/RMS, epilogue backward, transpose input gradient, edge gradient and sparse update, bias update, then generation publication on the caller stream. It keeps learned values in physical order and uses transpose maps referencing forward value positions. Its bias reduction is serial over rows for each of 16 channels, so a tiny launch-dominated speedup cannot establish large-scale efficiency. [S24]

The newer training_program_v2 files inspected validate program and graph-capture envelopes. They do not themselves invoke CUDA graph capture/instantiation. Actual graph use appears in tests and caller-controlled paths. Preserve that distinction when presenting runtime capabilities. [S15, S24]

4.6 A genuinely biological execution path

Sequence integration supports a bounded motif predicate over packed DNA, coordinate-to-regulatory mapping, and regulatory-to-gene accumulation. It can materialize a predicate mask, materialize a relation, or fuse the predicate into accumulation. Cached artifacts carry sequence/predicate/coordinate/projection identities and CUDA readiness. Its selector compares first-use versus cached-use costs over expected reuse, with evidence compatibility checks. [S25]

This is an excellent architectural case study: biological meaning identifies a computation that should remain unchanged across many changing cell states. It is also a warning against treating the newest operation enum as the whole product: this executable core-v1 operation is absent from the v2 eight-kind vocabulary.

5. What the performance evidence actually establishes

The reviewed CE-GEO N64 fixture has 64 destinations, 64 sources, and 2,176 logical edges, of which 2,048 are a deliberately dense fragment and 128 are residual. Its reported cold and steady costs are:

Path Accounted cold phases Steady consumer-complete time
Hybrid 123.953 microseconds 39.474 microseconds
cuSPARSE comparison 4,139.683 microseconds 36.840 microseconds

The derived average at reuse 16 is 47.221 microseconds versus 295.570 microseconds. However, cuSPARSE is faster in steady execution, with an algebraic crossover around 1,525 uses under these recorded phase costs. This is evidence that lifetime matters—not evidence that hybrid is universally faster. [S26]

The benchmark source materially narrows interpretation. Its “semantic search” constructs a predetermined exact cover; it does not execute the general production geometry optimizer. The sparse cold phase includes handle/descriptor creation. Some allocations and construction lie outside the accounted phases. The timed iterations include H2D input/value uploads, D2H output, and stream synchronization. Hybrid uses half inputs/weights, while the comparator expands the same rounded data to float. The comparator is cuSPARSE's default algorithm, not a demonstrated exhaustive strongest-baseline selection. The order of timed paths is fixed. [S26]

These choices can be legitimate for a stated scenario. They cannot support an unqualified claim about full compiler preparation, resident repeated biological computation, or all available baselines. Future receipts should separately report process initialization, relation preparation, value preparation, resident execution, transfers, and consumer readout.

The aggregate microarchitecture report also records missing requested Nsight counters despite a capture artifact being present. Do not infer memory throughput, occupancy achieved, or cache behavior from unavailable counters. The newer CE-EXOP readiness receipt explicitly has no runtime timing or Nsight evidence. The small training and sequence timings quoted elsewhere are reports embedded in source comments; they should be reproduced on larger workloads before promotion. [S24–S26]

A better evidence unit: a candidate/workload/numerical-policy/target/source-build tuple with an execution witness, independent correctness result, preparation and lifetime breakdown, memory peak, uncertainty, baseline definition, and clear limits. An inventory entry, resource receipt, compile success, or passing capability-name test is not that unit.

6. Reconsidering the primitive algebra

6.1 The eight-kind enum is useful, but not a sufficient definition of biology-aware computation

The v2 core names apply, transpose apply, support contraction, segment reduction, segment normalization, edge map/gate, bundle apply, and sparse axis update. It also contains valuable numerical, determinism, output-order, ownership, and generation contracts. Those contracts often matter more to optimization than adding another operation name. [S12]

But the enum is simultaneously too coarse in some places and too narrow in others. Support contraction conflates incompatible interpretations across layers. Edge gating does not by itself distinguish numerical multiplication from logical exclusion. Bundle is often a composition, while sequence-predicate accumulation is executable but not represented in v2. A reaction, tree recurrence, or sequence-alignment frontier is not naturally described as one of these eight operations without losing the structure that makes it fast. [S05–S06, S18, S20, S22, S25]

Proposal: retain recognizable high-level operations, but give them a common lower semantic substrate:

Typed domains, axes, logical identity
  + explicit/implicit support generators
  + gather and pure local computation
  + reductions with specified partial-result algebras
  + writes, aliasing, mutation and publication effects
  + numerical and approximation permissions

This is not a proposal to lower everything immediately into arbitrary loops. Keep apply, contraction, normalized exchange, moments, and hierarchy visible as named patterns while they still enable profitable transformations. Lower only the information that a later stage no longer needs.

TACO's format abstraction and SparseTIR provide useful precedent for separating format, iteration, and transformation. They do not provide biological identity or prove that their complete architectures should replace Cellerator. SAM provides a related precedent for a streaming realization layer on spatial accelerators. [R01–R03]

6.2 Specific semantic changes worth testing

Split contraction meanings explicitly. For an edge e=(d,s), distinguish a scalar sum_k A[s,k] B[d,k], a vector A[s,k] B[d,k] retained for every k, and a reduction across selected edges. Splitting k in the first requires numerical partial sums; splitting k in the second produces disjoint outputs. The existing support-embedding contract asserts the second while the native contraction kernel implements the first. This cannot be solved by a harmless adapter rename. [S18, S20]

Separate support from weights. An absent edge, an inactive mask entry, and a present edge of numerical weight zero are distinct under important numerical policies. The compiler should know when it can replace one by another. A “gate” should state whether it is applied before normalization, after normalization, to the message, or to membership itself.

Make write semantics independent of operation names. Unique-index update, reduction-scatter, atomic accumulation, deterministic segmented accumulation, and publication are different effects. Sparse update is not an appropriate semantic substitute for every state-changing composition.

Treat transpose as a semantic view and a physical planning opportunity. The mathematics can be orientation-independent while execution is radically different. Shared edge identity enables shared values and gradient mappings; it does not force forward and transpose to share the same tile layout.

Keep mergeable states first-class. The existing centered moments and log-sum-exp state interfaces are valuable. A semantic reduction state should define neutral element, accumulate, merge, finalize, numerical behavior, and deterministic-order restrictions. This exposes split-segment, multi-block, distributed, and streaming implementations without adding a separate opcode for every moment or normalization variant. [S18]

Keep compositions visible rather than expanding the primitive enum indiscriminately. Bundle, chain, many pooling/broadcast operations, and many biological conveniences should begin as library compositions. Promote a composition to a preserved semantic pattern when early decomposition prevents a demonstrated optimization. Exchange is such a plausible pattern because eliminating edge-score/probability materialization can matter. That does not require exchange to become an irreducible hardware primitive.

6.3 A three-level test for every abstraction

At the biological level, ask what identity, mechanism, invariant, or workload-family fact the representation preserves. At the operation level, ask what algebraic rewrites, partial-result decompositions, and materialization choices it enables. At the realization level, ask what exact loop ownership, physical order, memory traffic, and hardware instructions implement it.

An abstraction earns its place when an experiment can demonstrate one of those benefits. A biological label that never changes legal transformations or planning is descriptive metadata. A physical tile type embedded into semantic IR too early may erase more opportunity than it adds. A generic graph with opaque callbacks may preserve flexibility but prevent fusion. These are empirical tradeoffs, not matters of naming taste.

7. Operation-decomposition study

This section works from user-visible computations to executable alternatives. Proposed algorithms are not implementations added by this review.

Notation: E is logical edge count; S and D are source and destination counts; K is a contracted feature width; V is an output/value width; N is the dense width used by relation application. “Exact” refers to the specified mathematical/support semantics; floating-point reassociation still needs permission.

7.1 Regulatory propagation across many states

Biological operation: compute the effect of regulators, genes, modules, or other typed entities on destination state.

Semantic form: Y[d,n] = sum_(e:dst(e)=d) w[e] X[src(e),n], with source/destination identities, edge identity, numeric policy, active-support interpretation, and output-update semantics preserved.

Decomposition: partition destinations for disjoint ownership; partition source/edge components into partial sums; partition dense channels into disjoint outputs; or partition the relation into exact dense fragments plus residual. These choices already have useful contracts and implementations in Cellerator. [S12, S18–S19]

Realizations: a narrow state may favor row-masked or feature-major sparse execution; a wide state may favor coalesced CSR/feature-major traversal, dense fragments, or vendor SpMM. A high-degree, narrow row needs edge-parallel reduction, not merely more threads assigned to absent output channels. Dense-fragment selection must include conversion, packing, padding, residual work, output combination, and the next consumer's layout.

Preparation and reuse: cache topology and its inverse identity maps separately from packed values. Repack only the value generation that changed. Share geometry across multiple states only when it really has the same support and interpretation. Keep the result in the persistent order expected by the next operation. Canonicalize at a genuine interface or observation boundary, not automatically after each operation.

Biology-native opportunity: a fixed regulatory mechanism across many cell states can turn topology preparation into a long-lived asset. If the relation weights are also shared, cell/state dimensions can become a batch of right-hand sides. If weights vary independently by cell, that is a different batched problem; pretending it is one shared matrix would be wrong. If variation is factorized, the next decomposition becomes possible.

Falsification: if stable support lasts too briefly, physical reordering costs dominate, or the input/output must be canonical every call, expensive geometry compilation may lose to a direct sparse baseline. That result should cause a cheaper preparation strategy, not a forced attempt to justify the existing geometry pipeline.

7.2 Exact factorized biological gates

Biological operation: modulate a shared regulatory mechanism by source availability and destination susceptibility.

Explicit model contract: R(c) = diag(a(c)) R0 diag(b(c)) for state c. This must be supplied by the model or proved from its expression, not guessed from correlated observations.

Transformation: R(c) X(c) = diag(a(c)) [R0 (diag(b(c)) X(c))]. Instead of constructing a distinct E-entry weight array for every state, perform source-wise scaling, one shared relation application, and destination-wise scaling.

Physical alternatives: fuse source scaling into gathers; fuse destination scaling into the epilogue; cache the common R0 geometry and packed weights. Batch states when storage and model semantics allow it. If gates are piecewise shared by cell groups, prepare one grouped schedule per sufficiently stable regime rather than every cell independently.

Cost: potential savings are O(E) dynamic edge-weight formation per state versus O(S+D) gate representation, with extra multiply costs at the chosen fusion points. Whether this wins depends on E, dense width, reuse, register pressure, and whether the original weights were already cheaply available.

Generalization: an exact finite basis R(c) = sum_b alpha_b(c) R_b exposes a relation bundle without materializing every cell-specific matrix. This is not automatically low rank; it is a model-supplied factorization. Too many basis relations, poor support overlap, or expensive source gating can erase the advantage.

Why this matters architecturally: the strongest optimization comes from retaining the way the biology constructs the relation, not merely inspecting the final CSR geometry.

7.3 Relation application composed with dense feature transformation

Operation: apply a regulatory relation and a dense change of feature basis: Y = R X W.

Alternatives: evaluate R (X W) or (R X) W. The first has approximate arithmetic proportional to S Fin Fout + E Fout; the second to E Fin + D Fin Fout. Intermediate shapes and transfer costs differ too.

Legal transformation: requires compatible axes, no intervening nonlinearity or stateful effect, and an appropriate floating-point equivalence policy. A biological identity relation must not be confused with a numeric reshape.

Realization: a compiler-visible composition can choose the cheaper order and jointly plan persistent layouts. A C++ semantic graph can expose exactly the same opportunity. Two unrelated eager calls generally cannot safely infer and reorder future work.

Reuse: a projection W reused across many state updates may favor a different order from a one-shot transform. The planner must consider whether the intermediate serves additional consumers. This is a good early test of whether graph visibility produces actual performance beyond a collection of fast primitives.

7.4 Forward, transpose, edge gradient, and update

For Y = R X, the basic derivatives are dX = R^T dY and dw[e] = dot(dY[dst(e),:], X[src(e),:]).

Preparation: one logical edge identity can connect forward values, transpose traversal, gradient output, optimizer state, and updates. A transpose index map can point back to the same physical value array. The existing native training slice demonstrates this approach. [S24]

Decomposition alternatives: destination-owned forward plus source-owned transpose; two distinct covers sharing topology; per-edge contraction; split-K edge-gradient reduction; or fused gradient/update when the old value generation is no longer needed. Dense fragments useful for forward may not be useful for edge gradients: the latter's reuse, output geometry, and reduction dimensions differ.

Execution order: all consumers of the old weights must complete before an in-place update overwrites them. Publishing a generation event on one stream is useful, but not a substitute for tracking all outstanding readers on other streams. Prepared state needs either explicit single-stream ownership or a defined concurrency protocol. Immutable snapshots/double buffering are alternatives when concurrent readers are required.

Fusion: keep activation epilogues with forward output when ownership is local; retain only backward-required quantities. Recompute cheap intermediates only when the memory saving exceeds repeated arithmetic. Bias-gradient reduction deserves its own scalable strategy rather than being left serial because a tiny fixture is launch-bound.

Numerical issue: half-stored learned values can lose small updates. The library should expose the existing storage/multiply/accumulation distinctions and allow master-state or compensated update strategies when the consumer's accuracy contract requires them. This is a workload choice, not a compulsory move to a general optimizer framework.

7.5 Support-restricted contraction

Operation: compute one scalar score for each existing relationship, z[e] = sum_k A[src(e),k] B[dst(e),k].

Semantic prerequisites: distinguish this from an edge-channel vector. Preserve the logical support and edge output order; do not silently merge duplicate relationships unless the operation's law permits it.

Sparse realization: thread per edge for tiny K, warp per edge for moderate K, CTA or split-K for large K. Splitting K produces partial sums; splitting edges produces independent outputs. A degree-aware destination grouping can reuse B across many source gathers, but may worsen load balance.

Dense realization: form a score tile for a sufficiently dense source×destination fragment, then map valid edge scores to their logical/physical edge slots. The dense option computes extra scores; it wins only if saved loads and matrix throughput exceed padding, packing, extraction, and residual cost. K and support density should both enter the decision.

Existing implementation: sparse and rectangular WMMA paths exist. Repair/verify rectangular alignment contracts before broader reuse. Do not infer that the exact support census provides all operand alignment guarantees. [S20]

Fusion: when a score feeds a simple edge map, fuse that map into score production. When it feeds normalization and aggregation, preserve the larger pattern for the next section. When all scores are externally observed or needed by a backward pass, materialization may be the right choice.

7.6 Sparse biological exchange: score, normalize, aggregate

Consider scores q[e] = dot(Q[dst(e),:], K[src(e),:]), a typed edge transform, normalized weights over each destination's active support, and Y[d,:] = sum_e p[e] V[src(e),:].

The current fully fused implementation risks O(E K V) score recomputation. The right comparison is not simply fused versus unfused; it is a set of ownership and materialization strategies. [S23]

Alternative A: staged score computation plus fused normalization/application. Compute each q[e] once with an edge-balanced contraction kernel. Then process destination segments, retaining their probabilities or normalization state as appropriate. This accepts one global score array to preserve parallelism for expensive K or very irregular degrees.

Alternative B: shared-memory tile fusion. A block owns a set of destination rows, distributes edge scores across warps, then changes the intra-block work mapping for segment normalization and feature aggregation. This avoids recomputation without forcing the same thread layout onto three different operations. Dynamic fusion research such as DF-GNN directly addresses this scheduling problem. [R05]

Alternative C: online normalized weighted reduction. A partial segment carries (m, l, z), where m is its maximum score, l its sum of scaled exponentials, and z a V-vector of scaled weighted values. Merge two partials using:

m = max(m_a, m_b)
l = exp(m_a-m) l_a + exp(m_b-m) l_b
z = exp(m_a-m) z_a + exp(m_b-m) z_b
Y = z / l

Compute each score once, then update its contribution to the V-vector. The mathematical work remains O(E(K+V)), though practical tiling may deliberately recompute some terms to control storage. Register pressure grows with V; split very large segments and merge states when necessary. Empty segments, NaNs, positive infinity, and all-negative-infinity segments require an explicit shared policy rather than borrowing incompatible behavior from different kernels.

The online normalization principle is established prior art, including FlashAttention; it is not a newly invented Cellerator algorithm. The Cellerator-specific opportunity is combining it with stable biological support, persistent identity/order, typed gate semantics, and reusable relation preparation. [R04]

Backward choices: save normalization statistics rather than all edge probabilities; recompute scores when cheaper than loading them; share support and gradient mappings. If the caller needs edge weights as outputs, a no-materialization plan is not legal. Gate placement must remain explicit: multiplying logits is not the same operation as masking edges or multiplying normalized messages.

Falsification: if V-state register pressure destroys occupancy, if degrees exceed useful block ownership, or if score reuse across many consumers dominates, staged execution should win. The planner should preserve all three alternatives rather than declare full fusion the universal target.

7.7 Segmented statistics and normalization

Biological operation: aggregate cells, genes, regions, modules, or time segments; compute statistics used by a later state transformation.

Semantic form: a segment or incidence relation plus a reduction state. The existing centered moments state (n, mean, M2) already supports stable merging. Use it for variance where stability is required rather than assuming the existing raw first/second-moment CUDA kernel is equivalent numerically. [S18, S21, S23]

Decomposition: tiny segments can share a warp/block; moderate segments can have one cooperative group; huge segments should split into partial states and merge. Vectorizing across dense features can improve contiguous accesses relative to assigning every thread the same feature and striding through rows. Weighted moments need a defined weight interpretation and merge law, not an improvised extension of integer count.

Normalization: a later transform may consume only the aggregate statistics. For RMS or L2 normalization, fuse the scale into the next operation when there is no need to write a separately normalized array. When both original and normalized states are observed, preserve both or explicitly reuse storage with ownership permission.

Reuse: static segment membership permits persistent offsets and work partitions even when values change. Hierarchical segments can reuse subtree membership and partial states. Mutable membership invalidates these artifacts separately from value updates.

7.8 Hierarchical pooling, broadcast, and tree computation

Operation: pool lower-level entities into biological groups, then broadcast group state back, or traverse a genuine ancestry/compartment tree.

Simple decomposition: represent pool as an incidence reduction; represent broadcast as an identity-preserving gather. Avoid materializing a full broadcast matrix. A fused producer can update group partials when ownership is compatible. Multi-level pool can reduce through hierarchy levels or flatten membership if that preserves semantics and is cheaper.

Important distinction: a hierarchy used merely for grouping is not automatically an exact quotient of the original dynamics. To evolve a reduced state exactly, a condition such as R P = P Q and suitable closure of any nonlinear operations is required. Cluster labels alone do not supply that proof.

Beyond aggregation: a tree-structured linear solve or recurrence deserves a structure-preserving representation. Arbor's Hines-matrix implementation separates static construction, dynamic assembly, and tree-structured solution, illustrating how biological morphology can select an algorithm rather than just a sparse format. Forcing such a problem through repeated generic relation applications can erase the direct solver structure. [R12]

The immediate recommendation is not to implement a neuroscience simulator. It is to test whether Cellerator can host a tree recurrence/solve as library mathematics with a useful semantic contract, without pretending the current relation enum exhausts biology.

7.9 Bundles and chains of relations

Bundle: Y = sum_t R_t X_t. Alternatives include sequential applications into one accumulator, one traversal over a tagged union of edges, grouping relations with shared sources/layouts, or producer fusion with shared input loads. The existing callback bundle is sequential; a helper that reduces already computed outputs is not evidence of shared relation traversal. [S23]

Preparation may be shared across relations only where axes, support, or transformations actually coincide. Different relation types may require different value laws and masks. Preserve typed relation identity while permitting a physical union.

Chain: Y = R2 (R1 X). Candidate choices are materialize the intermediate, fuse a bounded neighborhood with halo/recomputed intermediates, or compose the relations. Composing sparse matrices can introduce massive fill-in; a fused traversal can recompute R1 X for every downstream consumer. Neither is automatically superior to a well-laid-out intermediate.

The useful planner question is how much each intermediate is reused, whether it fits in cache/local memory, and whether a stable biological partition makes the chain locally closed. A local motif or compartment boundary can sometimes justify a compact fused subprogram. Generic “chain fusion” does not capture these conditions.

7.10 Dynamic support and incremental state changes

Operation: update a small subset of weights, edges, masks, or state coordinates and re-evaluate affected biological state.

Separate immutable topology, active mask, values, and physical geometry generations. A mask update need not force geometry reconstruction. Conversely, treating a now-absent edge as a numerical zero must be justified by the reduction's semantics.

A masked traversal versus a compacted traversal has a simple lifetime decision: compact when its construction cost is less than expected future uses times the per-use saving. Add costs for value remapping, transpose mappings, and any affected consumer—not only the immediate forward kernel.

For a linear operation, changes can be propagated algebraically:

(R + dR)(X + dX) - R X = R dX + dR X + dR dX.

The cross term matters when both change. Sparse perturbations can therefore induce a small exact work frontier. But nonlinearities, normalization, and long-range connectivity may expand the frontier quickly. Maintain a measured switch to a full recomputation rather than assuming biological perturbations remain computationally local. Floating-point reproducibility may require a specified accumulation policy or periodic reconstruction.

Potential preparation: dependency indices, reverse incidence, touched-row sets, edit logs, and persistent partial sums. A base-plus-delta relation representation can retain unchanged prepared fragments while rebuilding only affected regions. Its value is greatest when edits are genuinely sparse and repeated execution follows each edit.

7.11 Sequence-grounded regulation

Operation: map sequence predicates to regulatory intervals and then to gene-state accumulation.

Existing chain: packed sequence + predicate + coordinate identity -> predicate evaluation -> optional bitmask or coordinate relation -> regulatory relation -> accumulation. Cellerator already has fused, first-materialization, and cached-materialization choices with reuse-aware selection. [S25]

Improvement directions: share predicate results across many cell states; index multiple typed interval overlaps where the model requires them; reuse motif evaluation across related sequences with localized variants; fuse cheap predicates only when reuse does not justify materialization; preserve sequence orientation and coordinate identities through any physical permutation.

The current implementation is bounded: its inspected predicate support and interval mapping are not a general sequence-query compiler. Expand according to a real consumer's required motif/interval semantics, not a broad bioinformatics checklist. Sequence I/O, annotation databases, and workflow orchestration can remain external.

7.12 Reaction systems and rule-structured biology

A biochemical rate calculation naturally has a structure such as dx/dt = N v(x): local nonlinear rate expressions followed by sparse stoichiometric accumulation. Repeated reactant combinations may share subexpressions; small integer stoichiometry can specialize arithmetic; a dependency graph can limit recomputation after a local event. Conservation identities are useful only when supplied or proved for the actual model.

Rule-based systems can represent many species/interactions without enumerating every network edge. BioNetGen and exact hybrid particle/population research demonstrate that the representation and simulation algorithm can change while preserving specified biochemical semantics. This is a concrete reason not to define all future biological computation as an explicit sparse relation. [R10–R11]

Possible Cellerator chain: typed reaction/rule library object -> shared local expression graph and support generator -> dependency-aware partial updates or batched rate evaluation -> stoichiometric reduction -> state update with explicit numerical/time-integration semantics. Keep the scientific model and solver policy outside the low-level engine unless an actual performance need justifies their inclusion.

7.13 Sequence alignment and other recurrences

Wavefront alignment is another caution against a universal SpMM worldview: useful performance can depend on sequence similarity and the frontier of a dynamic program. WFA2 provides exact modes as well as optional heuristic modes; an architecture must not confuse them. [R13]

Cellerator need not reimplement an alignment toolkit immediately. It should be able to host a recurrence/frontier primitive or invoke an optimized external implementation while preserving enough biological structure to select the right algorithm. A source language capable only of decorating relation application would not automatically make this workload natural.

8. Biological optimization opportunities beyond generic sparse algebra

8.1 Make the unit of preparation a biological computation family

Architectural hypothesis: a particularly valuable prepared object is a family with a shared biological domain, common support or support grammar, a variation program, and declared observation/update boundaries. Its artifact may contain common geometry, a dictionary of recurring motifs, edit maps, per-regime candidate choices, and optional specialized code.

This is more expressive than preparing one matrix. It may be less expensive than independently compiling every state-specific matrix. It also matches the existing sequence cache and fixed-topology training ideas better than a source-file-centric product definition.

Its falsifier is straightforward: if related states share too little support or legal computation, family maintenance and dispatch overhead will dominate. Then independent prepared operations are the right answer. The system should support both without assuming a universal family abstraction.

8.2 Shared ancestry and base-plus-edit geometry

Biological ancestry can provide a constructive explanation of similarity, not merely an empirical correlation. Tree-sequence algorithms exploit differences between neighboring genealogies rather than rebuilding every tree. The relevant precedent is incremental structure traversal, not an assertion that regulatory networks obey the same representation. [R09]

A Cellerator experiment could represent related biological structures as a prepared base plus typed additions, removals, or parameter changes. Rebuild only invalidated fragments, preserve logical identity, and reuse unaffected transpose/gradient maps. The experiment must compare against ordinary structure-based caching and include workloads where edits are not small.

8.3 Support dictionaries and repeated motifs

Repeated exact neighborhoods or support motifs can share index storage, gather schedules, and preparation. If values are unrelated, this does not automatically permit sharing arithmetic results. If a model additionally gives shared weights or a certified factorization, shared partial computations may become legal.

A useful representation could separate motif identity, entity renaming/permutation, coefficient parameters, and exception edges. This might benefit repeated compartments, regulatory motifs, or incidence patterns. Measure dictionary construction, decoding, exceptions, memory traffic, and gradient/update cost. A compact representation that introduces random decoding on every edge may be slower than CSR.

8.4 Mechanism mixtures

A biological relation may combine a local interval/stencil mechanism, a tree or compartment mechanism, a shared module mechanism, and irregular long-range edges. Represent those mechanisms separately when they enable distinct algorithms; do not immediately flatten them into one CSR and ask a rectangle search to rediscover the structure.

Examples are proposals, not universal biological facts. The same data may lack any profitable mechanism decomposition. Cellerator should accept externally supplied structured generators and retain a generic explicit-support fallback.

8.5 Exact repeated product structure

A model constructed as repeated compartments × molecular species may have an operator represented by a Kronecker sum or product. Such an operator can be applied without materializing the lifted edge set. Local reactions and inter-compartment transport may also have different update frequencies.

This opportunity comes from the model's construction. Biological labels alone cannot certify separability. An explicit construction can, and should survive into planning. The test is whether factorized execution saves total work and storage after accounting for layout changes and coefficient updates.

8.6 Biological semantics as transformation permissions

Certain model-level facts can permit transformations unavailable to a generic numerical kernel: exact factorization of gates, known disjoint compartments, a conservation law, a symmetric interaction, a bounded support generator, or an exact quotient. Statistical correlations can guide candidate selection but cannot establish these laws.

Use four provenance classes: proved from program construction; explicitly asserted by the model with an optional verifier; validated for the loaded instance; and estimated from representative data. Only the appropriate classes should authorize semantic transformations. Approximate scientific transformations require an explicit error/model contract and a way to measure their downstream effect.

8.7 Identity-preserving stochastic and reproducible execution

Physical reordering must not silently reassign random variates to different cells, genes, edges, or events. One possible design is counter-based random generation keyed by stable logical identity, step/event, and stream/subsequence rather than thread position. Random123 provides established counter-based machinery; the Cellerator contribution would be the identity/effect contract around it. [R14]

This does not automatically make a stochastic simulation invariant to all event-order changes. Event causality and numerical schedules still matter. It does make a simple permutation of physical storage less likely to change which biological entity receives which random input.

8.8 Workload prediction from meaning

Meaning can tell the planner that a sequence predicate is invariant across a training epoch, that topology persists while values update, that a transpose follows a forward pass, or that a hierarchy will be traversed repeatedly. Those facts inform preparation amortization before timing begins.

The important distinction is between a declared reuse horizon or effect contract and an optimistic historical average. Record uncertainty, permit early invalidation, and avoid expensive specialization when the remaining horizon is unknown. This is how biological information can improve execution without making programs brittle.

9. Standard-library design from first principles

9.1 The boundary should follow semantic responsibility

The base language should provide the mechanisms needed to express and preserve identity, types, effects, composition, and expert control. It should not recognize every useful biological function by its source spelling. Library code should express reusable constructions, with selected operations lowering to shared semantic intrinsics whose identity is resolved through symbols/types rather than a literal ce::name string scan.

The native engine should own preparation, candidate registration, execution contracts, backend dispatch, caching, and the implementation of fundamental semantic operations. The .cell library should own transparent compositions and biological abstractions that are profitable for the compiler to inspect. The C++ facade should expose the same concepts and the same underlying operations, not a second independently defined algebra.

Templates are valuable for scalar/storage/accumulation policy, axis roles, small static dimensions, local pure maps, and structured constructors. They should not generate a distinct enormous kernel for every biological entity ID. Stable identity is usually data, not a C++ template argument.

9.2 What belongs in the library

A useful initial library has four substantive layers:

Layer Facilities Why it belongs
Core structured mathematics Apply/transpose, support dot, map/gate, segmented reductions and normalization, explicit updates Small reusable mathematical foundation
Structure-aware composition Bundles/chains, moments, incidence pool/broadcast, persistent-order helpers, masks and relation-family construction Exposes shared preparation and fusion
Biology-specific constructions Regulatory propagation, factorized gates, module/compartment composition, sequence-derived relation facades, optional reaction/tree helpers Supplies meaning or construction facts not visible in raw arrays
Expert and interoperation Graph/IR builders, plans, profiles, candidate forcing, backend registration, borrowed memory, streams, identity adapters Preserves low-level power without burdening simple users

The first layer can be biology-agnostic mathematics over biologically meaningful structure. The third must do more than rename generic graph operations: it should construct legal structure or supply useful invariants.

Do not make full file-format ingestion, annotation downloading, preprocessing pipelines, generic neighbor-search workflows, plotting, a general model-training framework, or an entire biological theory part of the fast-math core. Some existing adjacent support/feature/legacy-ML code is build-reachable; classify it by actual consumers before relocating it. Interoperability with such software is valuable and should remain possible. [S29]

This makes co-ownership and module tests easier, especially if modules become independently consumable. Neither option should require moving every existing file before delivering useful math. First establish semantic owners and target dependencies; migrate one validated vertical slice at a time.

9.4 Installed layout and umbrellas

A proposed installed layout is native headers under include/Cellerator/, native libraries under the normal library directory, language sources under share/cellerator/library/, profiles/schemas under versioned resource directories, and exported CMake targets corresponding to real linked functionality.

Use a small native umbrella such as Cellerator/math.hh for ordinary math, with expert/IR headers separate. A language umbrella can expose the common operations while specialized modules remain explicit. These names are design sketches, not claims about existing usable imports.

The current stdlib/manifest.json identifies a core source resource and version constraints; the installer still owns stdlib/. Reconcile those rules with library/ only after its actual source bodies can be reviewed. Compatibility resource paths can temporarily forward to the new location. Do not silently ship both as independent standard libraries. [S01]

9.5 A shared semantic definition without overbuilding generation machinery

A compact operation definition can specify type/axis rules, effects, numerical behavior, reference semantics, and recognizable compositions. Both frontends lower to that definition. Native and source-library convenience functions may differ in syntax and ergonomics while producing equivalent graphs.

It is not necessary to auto-generate the entire compiler and every header from a giant schema. Start with a small shared semantic contract and conformance tests. Add generation only where it removes demonstrated duplication without obscuring executable behavior.

10. libCellerator as a first-class product

10.1 Five user modes

User Required experience Appropriate underlying layer
Simple C++ fast-math caller Bind arrays and typed relations; call math; obtain a correct fast default Eager convenience API backed by prepared primitives
GlassHelix-like consumer Reuse structure, update values, supply caller streams/workspaces, compose forward/backward work Prepared operation/program API
Composition-aware C++ expert Construct the same graph the language can expose; inspect transforms and costs Shared semantic graph and planning API
Compiler embedder Parse/analyze/inspect/lower/emit without command-line coupling Compiler library components over the shared engine

These layers should be independently useful. A simple caller should not need an execution field, source parser, profile file, candidate identifier, or an IR tutorial. An expert should not be prevented from accessing them.

10.2 The simple path

The desired conceptual sequence is: create a relation view with identities and index arrays; bind state/value buffers; choose a numerical policy; call apply or prepare it for repeated use. The API should allow caller-supplied allocation, stream, workspace, and memory location, but supply convenient defaults when unambiguous.

A preparation request can accept optional representative information and expected reuse. Missing hints should select a safe generic path, not make ordinary correct mathematics impossible. An expensive optimized plan should never be forced merely because a profile was supplied.

The current internal/public typed APIs contain much of the necessary machinery, but the installed named library does not provide this coherent product. Fixing that is a small conceptual change with high user value; it is not just an API-aesthetics exercise. [S01, S12–S15]

10.3 The prepared path

A prepared object should state the facts on which it depends: topology identity/epoch, axis identities, order/projection, numerical policy, target/runtime, required buffers, concurrency rules, and any value-generation-dependent artifacts. It should expose a cheap validity check, rebindable data, and a clear distinction between immutable structure and mutable values.

For a GlassHelix-like caller, the valuable unit may be a forward/gradient/update subprogram rather than one kernel. The existing native training path shows why: forward and transpose can share value positions and publication semantics. Generalize the useful mechanism without freezing its N16 model-specific composition as the universal API. [S24]

10.4 Expert and custom implementation access

Experts should be able to inspect or construct semantic graphs, request decompositions, obtain candidate frontiers, override a chosen plan, query workspace/resources, maintain persistent order, and invoke a typed implementation directly. “Force” should bypass profitability selection; bypassing semantic or safety validation should be a separate explicitly unsafe operation with visible consequences.

A custom candidate contract should include accepted operation semantics, shape/numeric/support constraints, preparation and value-update behavior, exact output/effect contracts, actual executable bindings, fallback behavior, measured provenance, and teardown/concurrency ownership. A symbol-less catalog entry must remain visibly non-executable.

The compiler and direct library should use this same contract. No C++ user should have to masquerade as a source-language program to access the best kernels.

10.5 What to stabilize

Stabilize biological identity, basic domain/axis views, numerical policy vocabulary, buffer/stream ownership, operation semantics, and simple preparation/execution/error behavior only after cross-layer tests validate them. Keep planning IR, provider interfaces, exact physical-layout schemas, and decomposition search explicitly developmental until real workloads exercise them.

Writable/inlineable IR is valuable when it exposes real optimization choices. A textual record that can be parsed and printed but does not affect execution is not sufficient. Each supported expert edit should have a verifier and a demonstrable lowering consequence.

10.6 Direct calls versus compiler-generated execution

A single direct apply and a single language apply should normally reach the same implementation portfolio. The language may outperform a sequence of eager C++ calls by seeing a larger composition. A C++ graph expressing that same composition should be able to achieve the same optimization quality.

Thus the natural performance distinction is opaque eager calls versus visible composition, not C++ versus Cellerator syntax. The language's additional value can be concise semantic construction, transparent inlining, safe propagation of identities/effects, and convenient expert control. Measure that value rather than treating language ownership as a prerequisite for optimization.

11. Geometry and representation model

11.1 Preserve the semantic/physical distinction

The existing separation lets biological identities survive reordering and lets multiple operations share meaning while choosing different layouts. It is worth preserving. The important extension is that semantic structure should not always require a globally materialized edge list.

Permit explicit support, an implicit generator, a hierarchy, a product construction, or a verified mixture. Physical realization can still choose CSR, feature-major masks, dense fragments, interval traversal, or generated code. A symbolic exactness certificate may sometimes validate a construction more cheaply than expanding every edge simply to prove it correct.

11.2 Fix preparation complexity before adding more search sophistication

exact_rectangle_census.cc builds a grid over source groups × destination groups and performs quadratic uniqueness checks over group tuples. For sparse biological relations, this can scale with the empty Cartesian product rather than the actual support. [S17]

The repository already has a sparse hash-based rectangle-counting and incident-edge incremental greedy implementation. Reuse or adapt that mechanism for an occupied-tile census. Compare hashing with sort-and-reduce and hierarchical bucketing; choose based on scale, allocator costs, and reproducibility. Exact cover validation also has a quadratic component-ID check that could be replaced independently of the linear edge coverage accounting. [S16–S17]

Avoid a simplistic “all quadratic code is bad” rule: small fixed metadata tables can reasonably use simple loops. The concern is quadratic work tied to biological domain size or unbounded candidate/component counts.

11.3 Physical order as a persistent asset

Make logical entity ID, logical edge ID, physical permutation, and projection-local value position explicit. Reverse mappings must exist when users observe canonical biological results, but need not be applied after every operation. Two successive operations with compatible physical domains should exchange data in that order.

Differentiate reversible permutations from semantic aggregation/coarsening. A reversible order change preserves identity; a quotient may lose distinguishability and needs a stronger mathematical contract. A generation update should invalidate only artifacts that depend on the changed fact.

11.4 Multiple representations can coexist

A relation can have a stable logical value authority with several physical read projections, or one authoritative physical order with reversible mappings. The choice should depend on update frequency and consumer mix. Do not impose canonical ownership merely because it simplifies one adapter.

Forward and transpose can share values through index maps, as the native training path does. If a dense tiled representation requires a second packed value array, keep it generation-indexed and account for its refresh cost. Dynamic masks should have separate identity from the base support whenever semantics permit. [S24]

11.5 Scale and ownership

The v2 operation schema uses 64-bit logical work/edge counts and 32-bit dense widths; it does not impose a 64-work-item limit. Several physical kernels use compact 32-bit local coordinates with 64-bit global bases, which is a sensible pattern. The remaining work is verifying every chunk boundary, product, launch-rounding calculation, and partial assembly—not replacing every local integer with 64 bits. [S12, S19–S22]

The JBC atom-fragment frontier has an explicit maximum of 64 candidates. That is a search bound, not a biological dataset-size bound. It should expose truncation and selection regret so that a bounded frontier remains an intentional cost/quality tradeoff. [S28]

12. Planner and optimization strategy

12.1 What already exists

The native end-to-end planner accounts for preparation, packing, kernel execution, epilogue, order transforms, transfer, synchronization, and communication. It distinguishes several reuse horizons. It uses analytical and empirical mechanisms. Its chain solver is dynamic programming over candidate transitions with deterministic tie breaking. [S14]

A separate Pareto helper is also real: it filters compatibility/correctness/quality/resource constraints, sorts by predicted end-to-end cost, and retains a frontier against total persistent-plus-transient memory. It is not a general multidimensional graph optimizer, but it is more than a placeholder. [S14]

12.2 Define the actual objective

The objective should be the lifetime cost of producing the required observations under memory, numerical, and latency constraints:

initialization actually charged to this workload
+ structure discovery and geometry preparation
+ optional code generation/compilation
+ all value-generation refresh costs
+ all executions and fusion/recomputation costs
+ layout conversion, transfer, synchronization and readout

Use expected remaining reuse, not an arbitrary amortization constant. When latency matters, represent cold latency and steady throughput separately rather than collapsing them into a misleading scalar. Memory peak is a constraint or additional objective, not only a sum of candidate workspaces.

12.3 Preserve local optimization where it is sufficient

A single independent operation can use a calibrated rule, small shortlist, or bounded empirical trial. There is no need to solve a global optimization problem for every sparse update. A linear composition with additive transition costs is a natural dynamic-programming case.

The existing chain DP retains the best analytical history per terminal candidate. That is appropriate only to the extent the state summarizes all future-relevant information and the analytical ranking is reliable. Shared prepared artifacts, memory lifetimes, fanout, and measured-model error may require retaining several histories or richer states. Measuring only selected terminal histories cannot recover alternatives discarded earlier. [S14]

12.4 Extend the search around real cross-operation costs

Promising state variables include current physical orders, selected shared preparation artifacts, live buffer lifetimes, partition/ownership choices, and numerical constraints. Treat a fused implementation as a candidate covering a subgraph rather than as a new global opcode for every combination.

Use small exhaustive or integer-optimization oracles for tiny graphs to quantify regret. Use bounded dynamic programming, k-best histories, or beam search for larger graphs. The existing two-dimensional Pareto helper may be reused, but distinct preparation, update, and multi-operation quality dimensions should not be assumed to survive its current cost/memory projection.

Learned cost models are optional. First establish reliable features, actual execution witnesses, phase accounting, and held-out validation. Otherwise a more powerful learner merely fits misleading labels. Use uncertainty to decide which candidates deserve measurement, and never autotune a state-mutating operation on live application state without safe snapshots or a non-mutating measurement setup.

12.5 Biology can reduce the search space

Known compartment boundaries, exact relation families, stable support epochs, typed source/destination locality, and anticipated transpose/gradient use can eliminate implausible decompositions before hardware tuning. This is a more distinctive role for biology than adding annotation names to a generic cost model.

The proof burden remains: a biological partition may be a locality hint, not a legal independent execution boundary. The planner must distinguish those cases.

13. Compilation, profiling, specialization, and JIT

13.1 Stage decisions when the relevant fact becomes known

Fact / decision Typical stage Artifact or action

Likely degrees, regimes, reuse, value distributions Representative profiling Hints, candidate priors, calibration—not semantic truth

The existing sectioned profile-artifact serialization is substantial implementation work: it has alignment, bounds, checksums, and pointer-free mapped sections. That is useful infrastructure. It is not by itself a profiler that discovers biologically profitable structure, nor proof that a profile's assumptions remain valid. [S10]

13.2 AOT and prepared execution

AOT should compile semantics and reusable kernels that do not require the actual dataset. Load-time preparation can compile data into geometry and execution recipes without generating machine code. This is already a meaningful form of compilation and is likely valuable for Cellerator even when no source language is involved.

The compiler can emit a prepared-program recipe whose binding phase validates actual structure. A native user can construct that recipe directly. Representative data can guide the recipe, but actual guards must ensure that incompatible real data uses a valid fallback.

13.3 Where JIT could outperform a finite catalog

JIT or offline structural code generation can specialize fixed small degrees, repeated motifs, incidence/rule generators, small constant coefficients, stable fused local programs, or exact model factorizations. It may remove index loads, branches, generic parameter decoding, and repeated address arithmetic that a finite portfolio cannot eliminate completely.

It can also lose badly through compilation cost, code-size growth, instruction-cache pressure, excessive unrolling, register pressure, or frequent invalidation. Generating one enormous program containing every edge of a large relation is usually the wrong first experiment. Generate recurring motif kernels or bounded local subprograms before attempting whole-dataset unrolling.

The current generated-C and narrow PTX paths show that some code-emission machinery exists. They do not establish a production JIT lifecycle with safe caching, runtime compilation, eviction, adaptive recompilation, and numerical validation. [S09]

13.4 Break-even and cache identity

Specialization is justified only when:

compile time + extra preparation + cache/maintenance overhead
  < remaining uses * per-use improvement.

For changing values, the per-use improvement must include repacking or parameter updates. For changing structure, expected invalidation must enter the remaining-use estimate.

Separate cache layers. Semantic code depends on operation/effect/numerical contracts. Structural specialization depends on the exact certified structure or generator and compiler/target identity. Physical geometry depends on structure, target, and layout choices. Packed values depend on geometry plus value generation. Binding state depends on buffers, residency, and concurrency ownership. A single undifferentiated “profile hash” is not sufficient.

If generated code embeds values, those values or their generation must invalidate it. Prefer runtime parameters unless constant folding is worth the additional recompilation dependency.

13.5 Determinism and unavailable JIT

Record selected candidate, compiler/toolchain version, target, semantic/geometry identities, numerical policy, and any tuning evidence used. Provide an AOT/candidate fallback when JIT is disabled, unavailable, or prohibited. Deterministic builds and runtime specialization can coexist when specialization artifacts are reproducible, identified, and exportable.

A model should not become incorrect because a representative profile is missing. The current compiler field policy requires either a representative profile or an explicit generic-reference profile. I recommend making the generic fallback a natural operational mode while keeping warnings and expert forcing available. [S05]

14. Hardware evaluation

CPU

CPU is useful both as an independent semantic backend and as a competitive execution target for small, irregular, or preparation-heavy workloads. The inspected host references and generated object demonstrations are not yet a coherent optimized CPU math SDK. Removing the CUDA build dependency from backend-neutral preparation and CPU execution has direct experimental value. [S01, S09, S11]

Potential CPU realizations include degree-bucketed CSR, feature-major support reuse, vectorized segment reductions, chunked formats, and structure-specific generated loops. SELL-C-sigma is useful precedent for exploiting SIMD while controlling padding and local row ordering. It is a candidate, not a universal replacement. NUMA ownership and thread scheduling should follow actual data residence rather than a GPU-derived partition. [R06]

V100 / sm70

Retain V100 as a serious optimization target. The existing exact support, feature-major, WMMA, transpose, and readiness work is valuable. Improve sparse and preparation algorithms alongside Tensor Core paths; the retained measurements already show that Tensor Core/output-ownership choices do not dominate every workload. [S19–S26]

Current toolchain reality matters: NVIDIA removed offline compilation and library support for Maxwell/Pascal/Volta from CUDA 13.0, while documenting continued use of the 12.x toolkits for those architectures. Pin a suitable 12.x lane for V100 rather than letting a global “latest CUDA” upgrade break the target. This does not mean existing V100 binaries cease functioning. [R07]

Newer NVIDIA hardware

Do not treat sm86 or later as merely larger sm70 tiles. Data movement, supported arithmetic, asynchronous pipelines, and the balance between matrix operations and non-matrix work can change the best decomposition. A separate provider can preserve identical semantic operations while choosing different physical representations and fusion granularity.

A recent example is FlashAttention-4's Blackwell-focused algorithm/pipeline co-design: its authors explicitly address matrix throughput scaling differently from other resources. The relevant lesson for Cellerator is to retune the entire decomposition, not to import that paper's speedup claims or assume its attention kernels solve biological exchange unchanged. [R15]

Exact structural sparsity must remain separate from approximate pruning. A hardware-friendly pattern is only legal when the real support or an explicit approximation contract permits it. A wider mixed sparse/dense portfolio is appropriate; forcing biology into a hardware pattern is not.

FPGA and other accelerators

Useful portable semantics include logical domains, relation generators, reductions/partial states, ownership, and stable identities. Warp layouts, WMMA fragment shapes, CUDA streams, and NVIDIA-specific value packing do not belong in those semantics.

A streaming realization layer could map support generators, gathers, local maps, merges, and state updates onto a spatial pipeline. SAM is a concrete research precedent. FPGA compilation latency makes repeated motifs, static topology, and long reuse horizons especially relevant; runtime values and masks should remain parameters where possible. [R03]

Do not design a lowest-common-denominator backend that weakens V100 kernels today. Preserve semantic independence and provider-specific realization instead, then test portability using one small workload whose FPGA/CPU decomposition is genuinely different.

15. Strong architectural alternatives

A. Prepared mathematics library with optional composition

Primary object: an efficiently prepared operation or hand-composed program. Preserves: current typed kernels, geometry, identities, value generations, native preparation, and the language as an optional client. Changes: makes installed native math and straightforward C++ ownership the immediate product; limits compulsory graph/IR machinery.

Expected consequence: the quickest route to useful performance when a few primitives dominate and hand-written compositions already capture the important fusion. It provides a strong baseline against which a broader compiler must earn its complexity.

Risks: eager boundaries lose cross-operation reassociation and shared materialization choices; each larger biological pattern may acquire another bespoke prepared API; a finite catalog can become difficult to maintain.

Discriminating experiment: compare a small suite of real prepared compositions against a common-graph optimizer. If the graph adds little beyond existing typed paths while imposing material overhead, retain this emphasis. If it repeatedly discovers substantial layout/fusion/reassociation gains that are burdensome to express by hand, move toward B.

B. Shared semantic computation engine with C++ and language frontends

Primary object: a typed biological computation graph and its prepared realization. Preserves: actual native implementations, semantic/physical separation, useful IR levels, and expert controls. Changes: eliminates independent semantic interpretations and connects both frontends to one operation/decomposition/preparation contract.

Expected consequence: allows global decisions about layout, shared preparation, contraction-normalization-application fusion, forward/backward reuse, and relation/dense reassociation. The source language can provide strong ergonomics without becoming a mandatory gateway.

Risks: graph/schema development can again outpace execution; representing every future possibility may overcomplicate the fast path; forcing a graph into tiny operations may add overhead. The engine must retain an inexpensive eager path and direct typed escape hatches.

Discriminating experiment: lower the same computation from a C++ graph and source representation, verify identical semantics and implementation availability, and compare against eager native composition. This alternative is justified by better execution and easier reuse—not by the existence of more IR files.

Assessment: this is the most plausible shared architectural destination, but its implementation should proceed through small working workload slices rather than a comprehensive rewrite.

C. Biological structure/family compiler with generative representations

Primary object: a biological mechanism or related family of structures plus a variation/effect program. Preserves: the native engine, candidate fallbacks, identity contracts, and optionally B's semantic graph. Changes: allows implicit support, motif dictionaries, exact model factorizations, ancestry/edit sharing, and optional structural code generation to be first-class.

Expected consequence: can eliminate entire materializations or repeated computations that a matrix-at-a-time architecture cannot see. This has the highest biology-specific upside.

Risks: stable/exact structure may be rarer than expected; inference of biological structure can be expensive or wrong; a too-specific representation may lock Cellerator to one model. JIT/code generation can overwhelm the saved execution time.

Discriminating experiment: exact factorized regulatory gates, a sequence-predicate family, and one controlled base-plus-edit workload against equally well-optimized explicit-relation baselines. Include negative cases with independent weights or high edit rates. If there is little net advantage, keep these as optional library constructions rather than reorganizing the engine around them.

These are development emphases, not mutually exclusive religions

A can deliver useful native math now, B can supply the shared semantic center, and selected C mechanisms can emerge where biology proves them useful. JIT versus AOT is an orthogonal staging decision, not a sufficient product identity. The evidence does not support deleting the compiler or making broad language expansion the next default task.

17. Code and target reorganization proposals

17.1 Reorganize around real dependencies

The useful target boundaries are approximately semantic/core contracts, geometry/preparation, planning, prepared execution/runtime, CPU backend, NVIDIA common/provider backends, source compiler, and optional interop. A public facade can link these deliberately; the installed target should not advertise them merely by installing headers.

Backend-neutral code should not require CUDA simply through an aggregate runtime dependency. CUDA-enabled builds should not define the only route to host preparation and CPU math. Public targets should reflect linked features and exported dependencies accurately. [S01,S11]

17.2 Separate executable registration from descriptive catalogs

Each implementation family needs a permanent owner for its code, constraints, preparation, launch binding, tests, and measured evidence. A catalog can reference these records, but should not independently restate unverified kernel facts. Keep compatibility adapters separate and visible.

Campaign portfolio names may remain as historical build/test aliases temporarily. The actual source ownership already lies largely in permanent directories. Rename only where it removes ambiguity or obsolete dependency coupling. Do not hide real functionality behind increasingly generic fan-in targets while leaving its registration disconnected.

17.3 Separate development history from public API meaning

Public filenames such as deliver_the_...milestone or freeze_... expose implementation history rather than durable concepts. Replace such names as APIs become real products, keeping compatibility forwarding headers when needed. The replacement should be accompanied by actual linking and conformance tests; renaming a declaration does not make it implemented.

Likewise, tests should be organized around semantics, decomposition, preparation, numerical policy, execution, installation, and backend behavior. Historical campaign acceptance tests can remain archived or labelled, but should not be the authoritative capability report. Benchmark evidence should retain immutable provenance rather than be silently relabelled as current.

17.4 What not to move or delete yet

Do not delete CP-BP/CellPack compatibility or the older training path merely because newer interfaces exist. Some are more executable than their successors. Do not delete the old atomic candidate when it serves a valid negative control. Do not move the inaccessible .cell library bodies blindly. Do not migrate every source before one externally consumable math slice works.

The reorganization should reduce the number of independent semantic definitions, accidental CUDA dependencies, and unreachable public APIs. A more uniform-looking tree is not a sufficient outcome.

18. Development-priority analysis

Immediate useful work

The first useful milestone should be an installed external C++ program that constructs a relation, executes it correctly, prepares it for reuse, updates values, and exercises one real forward/backward or exchange composition. It should work through advertised targets, not a hand-assembled list of internal source files. Keep one CPU semantic path and one V100 path visible.

Before broadening this milestone, resolve the contraction semantic conflict and the most concrete numerical/precondition gaps. A library built on inconsistent operation meaning will make later integration more expensive.

Architecture-validation work

Express the same small computation through native eager calls, a C++ semantic graph, and the source-language representation. Trace source/operation/candidate/stage identities to an actual launch. Verify that expert plan forcing changes execution when it should and is rejected when semantics are incompatible.

This tests B directly without requiring a full language implementation. It also establishes whether the current semantic/planning/realization hierarchy is useful or redundant in practice.

Performance experiments

Prioritize sparse exchange, sparse census preparation, persistent physical layouts across consumers, and degree/width scheduling. Include the vendor and simpler sparse alternatives under matching numerical and lifetime conditions. Add at least one biological construction whose representation can eliminate work, such as exact factorized gates or sequence-derived relation reuse.

Medium-term engineering

Unify semantic definitions, executable candidate registration, package exports, profile validity, preparation reuse, ownership/concurrency, and CPU build separation. Make missing capability states explicit. Extend the planner only when measured counterexamples show which state or search alternatives are missing.

Speculative/high-upside research

Explore relation families, support grammars, exact product structures, ancestry/edit reuse, generated motif kernels, incremental perturbation frontiers, and a small non-relation recurrence/tree workload. Preserve the ability to abandon an unprofitable representation without dismantling the core engine.

Where the project appears over- and under-engineered

Inference: compiler capability contracts, campaign-shaped interfaces, and layered descriptive schemas have advanced faster than their unified execution witnesses. That is over-engineering relative to demonstrated product capability, not proof those concepts are intrinsically unnecessary.

Inference: installed native usability, cross-layer numerical conformance, complete candidate reachability, realistic lifetime benchmarks, and scalable preparation are comparatively under-engineered. These are closer to the fundamental goal than another round of syntax coverage or cosmetic tree cleanup.

The recommended ordering is driven by information gained: first learn which existing machinery works as one product; then learn which representation/algorithm changes remove real biological work; only then freeze broader abstractions.

19. Critical experiments

E1. Capability must have an execution witness

Question: which advertised operations are actually usable through installed interfaces?

Build a tiny external consumer for each core family, using only exported targets and public headers. Trace input semantic operation to chosen candidate, prepared stage, and actual callback/kernel. Include a source-language variant for the subset it claims to compile. Distinguish declaration, compilation, linking, execution, numerical correctness, and measured performance as separate statuses.

Decision: no capability is “complete” merely because a constexpr table names it. Failure identifies the exact package/lowering/registration boundary to repair.

E2. One mathematical contract across layers

Question: do semantic IR, decomposition, CPU reference, and GPU implementation compute the same object?

Use support contraction with multiple edges and K=1,2,17,32; compare whole-K versus split-K assembly. Add an edge-channel product case to prove it is different. Test duplicate relationships, empty support, zero-size segments, high-bit-different identities, signed/zero weights, NaN/infinity policies, and cancellation-sensitive accumulation.

For rectangular WMMA, exercise legal and illegal strides/alignment explicitly. For sparse updates, distinguish unique from repeated indices. For runtime reuse, change one identity/generation at a time and verify only valid artifacts survive.

Decision: shared semantics must pass before broader adapters or compiler lowering are considered sound.

E3. Preparation scaling at fixed sparsity

Question: does geometry preparation scale with actual support or empty domain area?

Hold E approximately fixed while increasing source/destination domain sizes and occupied-tile dispersion. Compare the current census, occupied-tile hashing, sort-and-reduce, and any reused greedy index. Measure wall time, allocation count, peak bytes, exact-cover validation, and total cost over reuse horizons 1, 10, 100, and longer realistic runs.

Decision: use the simplest preparation algorithm whose lifetime cost wins. Reject an elaborate search that consumes more than it can repay.

E4. Sparse exchange without redundant score work

Question: when should the three stages share a kernel or materialize scores?

Vary K, V, edge count, degree skew, nonfinite policy, and whether edge probabilities are externally observed. Compare current unfused/current fused, staged-score plus fused tail, shared-memory scheduling, and online partial-state designs. Count effective score evaluations as well as time, bytes, registers, spills, and launch overhead.

Decision: retain multiple candidates with explicit conditions. A fewer-launch implementation that performs materially more arithmetic must win measured lifetime cost, not win by its name.

E5. Fair cold, prepared, and resident comparisons

Question: what is the real reuse crossover between sparse, hybrid, and vendor implementations?

Separate process/context creation, vendor handle creation, topology preparation, packing, transfers, resident kernels, and readout. Use matching input/output accuracy contracts and document storage differences. Compare relevant vendor algorithms, not only one default. Randomize or alternate measurement order appropriately, use repeated independent runs, and report distributions.

Decision: identify crossover regions, not a single universal winner. Reproduce the retained synthetic fixture, then move to biological structures with provenance.

E6. Persistent layout across a real consumer boundary

Question: do physical-order savings survive the whole computation?

Compare canonicalization after every operation with persistent order through forward, epilogue, transpose, edge gradient, update, and one final biological readout. Include the actual consumer's tensor layout, allocator, and streams. Measure value refresh, peak memory, and any extra transpose representation.

Decision: retain persistent order where net savings remain. A fast internal kernel is insufficient if every boundary repacks its output.

E7. Planner regret and state sufficiency

Question: are the existing DP and Pareto decisions close to the best feasible schedule?

Construct small measured graphs with two or three alternatives per operation, shared preparation, fanout, and memory constraints. Exhaustively enumerate or solve them with a small optimization oracle. Compare current chain DP, a k-best variant, and selected richer-state variants on held-out costs.

Decision: add only state/search complexity that reduces measured regret. This avoids rebuilding a sophisticated optimizer before its actual failure modes are known.

E8. Biological information ablation

Question: does biological meaning add execution value beyond generic structural statistics?

Compare identical computations with: structure-only features; biological annotation hints; and exact model-construction facts such as factorized gates or product structure. Use matched numerical semantics. Hold out whole donors, conditions, developmental regimes, species, or relation families where appropriate—not random edges from the same prepared object.

Decision: distinguish biology as a locality hint from biology enabling a new legal algorithm. A negative annotation result does not invalidate identity/reuse benefits, but it should stop claims of annotation-driven speedup.

E9. Generated versus catalog execution

Question: can structural specialization repay its cost?

Choose repeated small motifs, stable degree classes, or exact reaction/rule patterns. Compare a tuned generic candidate, AOT-specialized code, and optional JIT-generated code. Measure compile latency, executable size, register pressure, cache reuse, update invalidation, and remaining-use break-even. Include a structure-changing negative case.

Decision: introduce JIT only for families with demonstrated net gain. Otherwise retain candidate-based preparation.

E10. One architecture-independent semantic test

Question: is the computation model portable without forcing the same physical algorithm everywhere?

Use one relation/segment composition and one tree or implicit-support workload. Implement or evaluate CPU and GPU realizations independently; an FPGA/SAM-style realization can remain a later bounded experiment. Verify identity and numerical contracts while allowing entirely different layouts and schedules.

Decision: preserve useful semantics, not a universal physical tile representation. Portability should not mean emulating Volta everywhere.

E11. Related structures and sparse edits

Question: does a family/base-plus-delta representation save work after maintenance costs?

Use controlled and biological examples with known exact relationships between structures. Sweep edit rates, value update rates, and reuse after each edit. Include independent-weight cases where only index/preparation reuse is legal. Compare rebuild-all, reuse-common-geometry, and incremental affected-fragment execution.

Decision: promote family preparation only in regions where its maintenance and decoding costs are repaid.

20. Questions that remain genuinely open

The implementation and research evidence do not yet determine a single optimal final architecture. The following questions need real workload or execution evidence rather than another planning document.

Biology and workload: Which relations actually persist across GlassHelix computations, and for how many calls? Which values vary independently versus through exact source/destination gates or a small basis? How common are reusable support motifs, stable hierarchies, or sparse edits? Which outputs must remain individually observable? Are sequence-derived predicates reused across enough states to dominate their preparation?

Numerical meaning: What accuracy and reproducibility contracts do the scientific consumers require? When are reassociation, atomics, half storage, masked dense padding, approximate mechanisms, or reduced models acceptable? Can one reference backend define these policies without silently computing a different operation?

Architecture: How much benefit does visible composition produce beyond well-designed prepared C++ primitives? Does the existing multi-level IR preserve useful distinctions, or mostly duplicate identities and validation? Which current typed paths should become the shared implementation rather than be adapted through the older generic core? How much of the new library/ already expresses useful compositions, once its bodies are accessible?

Algorithms: Does occupied-tile preparation solve the main scale barrier? Which degree/width regions favor sparse, hybrid, or vendor kernels? When does exchange need staged scores rather than online fusion? Can gradients share physical preparation without paying excessive value mapping? Are exact biological family representations common enough to justify structural code generation?

Execution and systems: What is the correct concurrency ownership of prepared state and changing values? Which buffer versions may coexist? How often do cross-device or external-consumer boundaries erase layout gains? Which CPU workloads are faster without GPU preparation/transfer? What is the actual remaining reuse horizon for JIT or FPGA specialization?

Final judgment: Cellerator's current engineering contains real computational assets and substantial unfinished integration. Its most promising future is not established by either preserving or abandoning the compiler. It is established by making biological meaning reach executable decisions—and then proving that those decisions eliminate work, reduce memory traffic, amortize preparation, or improve hardware use on real biological computations.

A generic system could exploit many of the same algebraic facts if it were given them. Cellerator's potential advantage is to make those facts natural, explicit, persistent, and operationally useful in biological programs. That is a stronger goal than attaching biological names to sparse kernels, and a more testable one than declaring any particular language or compiler architecture the destination in advance.

Appendix B. Primary-source research bibliography

Research was consulted on 5 September 2026. These sources provide precedent or specific technical contracts, not predicted Cellerator speedups. This is a focused research set, not an exhaustive novelty search.

R01. Chou, Kjolstad, and Amarasinghe, Format Abstraction for Sparse Tensor Algebra Compilers, arXiv:1804.10112v2. Relevant distinction: sparse format/level capabilities versus computation and traversal.

R02. Ye et al., SparseTIR: Composable Abstractions for Sparse Compilation in Deep Learning, arXiv:2207.04606; ASPLOS 2023. Relevant distinction: composable formats and transformations rather than one fixed sparse format.

R03. Hsu et al., The Sparse Abstract Machine, arXiv:2208.14610; ASPLOS 2023, DOI 10.1145/3582016.3582051. Relevant precedent: streaming sparse dataflow realization for spatial accelerators.

R04. Dao et al., FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness, arXiv:2205.14135. Relevant precedent: tiled IO-aware computation and normalization-state reasoning; not a claim that dense attention kernels directly solve arbitrary biological support.

R05. Liu et al., DF-GNN: Dynamic Fusion Framework for Attention Graph Neural Networks on GPUs, arXiv:2411.16127v1. Relevant precedent: changing thread schedules across contraction, normalization, and aggregation; shared-memory versus parallelism-oriented fusion.

R06. Kreutzer et al., A unified sparse matrix data format for efficient general sparse matrix-vector multiply on modern processors with wide SIMD units, arXiv:1307.6209. Relevant precedent: SELL-C-sigma and controlled local sorting/padding for SIMD.

R07. NVIDIA, CUDA Toolkit 13.0 Update 3 Release Notes, section “Deprecated Architectures,” archive 13.0.3. Documents removal of offline compilation/library support for Maxwell/Pascal/Volta in CUDA 13.0 and continued 12.x build support for those targets.

R08. NVIDIA, CUDA Programming Guide, C/C++ language extensions, WMMA load_matrix_sync / store_matrix_sync. Documents 256-bit pointer alignment, half leading-dimension multiples of eight, and collective warp requirements.

R09. tskit developers, Tree Sequence Tutorials: Incremental algorithms. Relevant precedent: updating computations using differences between related trees rather than reconstructing every structure independently.

R10. Harris et al., BioNetGen 2.2: Advances in Rule-Based Modeling, arXiv:1507.03572; Bioinformatics 2016. Relevant precedent: rule-structured biological model representation.

R11. Hogg et al., Exact hybrid particle/population simulation of rule-based models of biochemical systems, arXiv:1301.6854. Relevant precedent: different representations and simulation strategies while preserving specified exact model semantics.

R12. Arbor developers, Matrix Solvers, official developer documentation; and Arbor – a morphologically-detailed neural network simulation library for contemporary high-performance computing architectures, arXiv:1901.07454. Relevant precedent: static/dynamic separation and biology-derived tree/Hines structure.

R13. Marco-Sola and collaborators, WFA2-lib, author-maintained implementation and documentation; original Fast gap-affine pairwise alignment using the wavefront algorithm, Bioinformatics, DOI 10.1093/bioinformatics/btaa777. Relevant precedent: recurrence/frontier algorithms where sequence similarity affects useful execution, with exact and heuristic modes kept distinct.

R14. D. E. Shaw Research, Random123, official C/C++/CUDA implementation and documentation. Relevant precedent: counter-based random generation; identity-keyed reproducibility is the proposed Cellerator integration, not a new RNG claim.

R15. Zadouri et al., FlashAttention-4: Algorithm and Kernel Pipelining Co-Design for Asymmetric Hardware Scaling, arXiv:2603.05451v1, submitted 5 March 2026. Relevant precedent: hardware-generation changes can alter the profitable algorithm/pipeline decomposition, not merely launch parameters.
