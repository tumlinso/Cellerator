# Autonomy, scope and integration rules

## Permission after the user's controller launch

The launched controller has permission to execute the entire accepted NF1 program with first-class agents in GlassHelix and Cellerator, including constructive changes to Cellerator. It may make engineering choices, publish developmental interfaces, issue normal claims, run tests under real leases, integrate, commit and intermittently push. It need not ask the user for each task, algorithm or coordinated API correction.

Permission is not delegated by package extraction or manual plan import. This distinction matters because native run metadata can already say active while every implementation task remains unclaimed.

## Scope is coordination, not an architectural cage

Task paths identify current ownership and initial proposed locations. They are not commands to preserve a poor design. If the best implementation belongs in an existing Cellerator owner not covered by the current claim, the controller transfers or enlarges the scope through the native workflow, checks conflicts, revises the handoff and then proceeds. Do not create a duplicate implementation merely to stay inside a directory.

Review existing completed work before rebuilding a capability. A task may resolve by demonstrating that the existing real implementation already satisfies its full acceptance contract, but the controller must record evidence, not infer completion from an old title. Novel scope beyond the foundation belongs in a separately approved program.

## Central changes

Each project has one central integration queue. Root CMake, public umbrella wiring, package exports and global registries are integrated by their assigned owner. Provider lanes can own focused build fragments explicitly assigned in the machine scopes. Request source-linked registration through the integrator; do not concurrently edit the same central file.

## Interface updates

Version 1 draft interfaces become developmental agreements when their owner completes the publication task. They are not eternal stable SDK promises. Changes require a version/hash change, identified affected consumers, refreshed scope/dependency context and rerun affected tests. A receipt pins an agreed source-dependent capability, not an abstract filename.

## Finished means integrated

A leaf produces source, tests and an honest handoff. A milestone joins producer commits and qualifies a coherent consumer. A final checkpoint requires current accepted evidence and a published source pair, not only local branches with passing tests. Merge onto each origin/main without force rewriting. Remove only owned, merged temporary worktrees and release leases/claims.

## Recovery under an unstable host

Prefer small meaningful commits and intermittent pushes. Save exact task/run/worktree identities and pending patches in authority. A killed gate leaves a pending/failed external receipt; rerun rather than editing it to passed. A failed import can have ambiguous outcome: inspect actual authority before retry. A worker crash cannot authorize `git reset --hard`, `git clean`, force-push or deletion of unknown work.
