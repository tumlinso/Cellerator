# Cellerator reuse and extension boundary

## Existing owners to inspect first

Operation-core v2, launch bindings and program/program_v2 provide the numerical/program path. The prepared relation pair supplies an actual N1/N16 forward/transpose and mutable-value spine. Projection value planes and atom-plane bindings already separate structural identity and mutable generations. Sessions, scratch, order maps, indexed gates, byte/bit support masks, segment operations, relation bundles and decomposition contracts are useful foundations.

The precise inspected paths and evidence are in `07_SOURCE_LEDGER.md` and `evidence/source_observations.json`. Some components are implementation-backed and source-linked but not one complete generic consumer surface. A schema enum, header or historical task closure is not proof that a requested route executes.

## Constructive additions

Expose focused native targets and separately linked consumer tests. Generalize the prepared program's multi-operand bindings and perform complete preflight before any stage submission. Separate immutable preparation from independent value/execution instances. Preserve existing pair behavior for qualified consumers rather than replacing it with a disconnected new engine.

Provide general-width FP32 reference-capable execution, a real indexed n-ary evaluator with explicit assembly, derivative actions, and legal support variants. Adapt existing gates/reductions/transposes instead of reimplementing them in GlassHelix. CPU reference mathematics can be deliberately separate for testing; production numerical ownership remains in Cellerator.

The current mutable spine is one owner stream/device with restricted external leasing and capture rejection. Respect those guarantees until an independently tested generalization replaces them. Do not describe a host-enqueued generation as completed GPU work. A failed partial submission can poison the execution instance; cannot claim rollback of in-place writes.

## Performance principles

Prepare cold structural maps once. Keep execution order through compatible operation chains. Bind mutable pointers, generations and scalar values without reparsing or topology discovery. Bound scratch and persistent storage, record cold preparation costs, and reject capacity failures before work where possible.

Optimize whole programs. Shared support across many instances, independent value planes, fused indexed nonlinear work, hoisted legal packs and shared subexpressions are promising. Result reuse requires complete dependency/generation keys; same address or same code is insufficient.

A compact active path wins only when saved work amortizes selection, compaction and preparation. Masks that change every step can favor direct predication. Per-cell activity must not automatically materialize an edge-by-cell matrix. Zero primal and derivative support may differ.

Retain sparse/vendor/dense-fragment alternatives and measured non-promotion. The RU1 record found no hybrid crossover on its bounded fixtures. This program must not promise one. Existing CE-AMP runs remain outside scope; new qualified targets do not silently activate historical permission gates.

## Central ownership

The Cellerator build lane owns its assigned focused build fragments and existing component build integration paths. The M integration lane owns root CMake and checkpoint integration. Other numerical lanes submit registrations and scope-transfer requests instead of independently editing central registries. GlassHelix workers do not write Cellerator source under a GlassHelix claim; the controller creates or dispatches the appropriate Cellerator first-class task.
