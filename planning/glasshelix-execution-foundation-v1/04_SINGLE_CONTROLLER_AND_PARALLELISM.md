# Single controller and first-class parallelism

## One strategic controller, two project authorities

Launch the program controller from GlassHelix after both manual imports have been verified. The controller owns the joint objective and schedules first-class lanes within each project's own run. A Cellerator lane is not a foreign child in the GlassHelix native run. Each local run has its own coordinator root and locally parented lanes.

Where tooling permits one agent to hold the two qualified coordinator contexts, the same controller can fill both seats. Otherwise it dispatches a first-class Cellerator coordinator as its program-level delegate. This delegate does not create a second competing strategic controller. The relationship is recorded in the joint manifest and handoff, not through a fictitious cross-authority parent_lane_id.

Every substantial implementation stream has a native lane, authoritative claim, workspace, dispatch and handoff. Local subprocess helpers are bounded assistants to one claimed task, not substitutes for first-class lanes. Discover current workflow tools in the A tasks; do not guess Codex CLI flags or reuse old task ids.

## Thirty named lanes do not mean thirty simultaneous agents

The paired catalog has 30 lanes including coordinators. Combined explicit dependencies, serial lane queues and external receipt edges produce a maximum coarse topological frontier of eight tasks in the delivered graph. That is a planning bound, not a hardware reservation or a promise that eight tasks should always run together.

Begin with source/authority and independent-oracle preparation. After the developmental contracts, build, lifetime, numerical and validation streams can fan out. Increase concurrency only within live CPU, RAM, disk and tool quotas. Serialize GPU evidence on the actual project lease and one shared host lock used by both repositories. Multiple per-project locks are not mutual exclusion across projects.

## Workspace modes

Implementation lanes use isolated_merge. Their own serial queue preserves local write order. The delivered validator checks unordered write overlaps, including parent path overlaps, even for isolated branches. This prevents avoidable central-file merge contests; it does not prevent the controller from transferring scopes through recorded workflow updates.

Before starting a task, integrate required producer commits into the task workspace or use an explicitly versioned artifact. A producer claiming done without its source available to the consumer does not satisfy the dependency. Interface agreement can release consumer design work; runtime acceptance requires actual linked execution.

## Autonomous decisions permitted

The controller may select ready work, assign/resume agents, adjust resource budgets, split oversized tasks, combine truly redundant tasks supported by live evidence, move useful implementation to its proper owner, revise provisional API spelling, select alternative correct algorithms, transfer scopes, and fix integration/regression failures without renewed per-task approval.

These changes must be recorded through the authoritative workflow. Maintain the scientific acceptance conditions, cross-project receipt validity, ownership and integrated path. Do not edit SQLite or generated Todo projections as a second task system. Do not weaken tests to match a broken implementation.

## Recovery and integration

Commit meaningful validated checkpoints and push intermittently through normal fast-forward-safe Git operations. A transient push failure should preserve local work and a recovery record, not trigger force push, reset or cleanup. Resume from authoritative task/dispatch status and actual commits, not remembered chat summaries.

After a worker failure, inspect the worktree and claim before reassignment. Never automatically delete another agent's unmerged work. Finish by integrating this program's commits onto each origin/main, verifying the final source pair, and cleaning only owned, verified-merged program worktrees. Unrelated historical worktrees remain untouched.

## Escalation

Ordinary implementation choices remain autonomous. Escalate only when proceeding would require destructive loss of unpreserved work, unsupported authority/resource access, a genuine contradiction in the user's scientific mandate, or scope expansion into a separate biological or distributed project. Insufficient GPU availability blocks the GPU gate, not all unrelated host work. An unavailable native mutation/dispatch contract is a tooling blocker, never permission for direct database edits.
