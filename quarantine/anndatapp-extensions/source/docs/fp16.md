# Binary16 storage

`anndatapp::Float16` stores one IEEE 754 binary16 value in its `std::uint16_t`
`bits` member. It is a trivially copyable two-byte type, distinct from both
`std::uint16_t` and CUDA's half type. `DType::float16` and `NativeType::half`
identify it in the ordinary AnnData array interfaces. Existing dtype enum
values have not changed.

```cpp
import anndatapp.core;

using anndatapp::Float16;
auto values = anndatapp::Array::empty<Float16>({2});
auto out = values.edit().dense<Float16>();
out.data()[0] = Float16::from_float(1.25f);
out.data()[1] = Float16::from_double(0.1);
float x = values.view().dense<Float16>().data()[0].to_float();
```

`from_bits` and `bits` expose the representation without a numeric conversion.
`from_float` and `from_double` round directly to binary16 using round to nearest,
ties to even. Conversion from `double` does not first round to `float`. Finite
overflow produces infinity; signed zero and subnormals are supported. Numeric
NaN conversions produce a canonical quiet NaN. `to_float` and `to_double`
convert the stored value; raw array and record copies preserve the stored bits
without conversion. Typed `uint16_t` access does not alias a `Float16` array.

Dense, CSR, and CSC arrays use the existing allocation, borrow, shared-owner,
adopt, selection, copy, and backed-transfer contracts. Scalar metadata retains
its binary16 dtype and numeric value, but does not promise to preserve a NaN
payload through a scalar conversion. Numeric columns and record members accept
binary16. Floating-point categorical dictionaries reject NaN and treat
positive and negative zero as the same value. As with the existing floating
dtypes, nullable floating-point columns are not supported by the AnnData file
codec.

H5AD uses a two-byte IEEE binary16 HDF5 floating-point datatype with the
requested file byte order. Zarr v2 uses `f2` with its byte-order marker; Zarr
v3 uses `float16` and the byte order of the bytes codec. Dense arrays, scalar
metadata, sparse value components, and supported backed reads and writes retain
their binary16 dtype. H5AD compound numeric record fields support binary16;
Zarr record-array codecs remain unsupported. Zarr missing-chunk numeric fills
round directly from the parsed double value, and v3 hexadecimal fills specify
binary16 bits exactly.

The pinned h5py and Zarr readers verified the physical encodings in both
directions. Pinned AnnData 0.13.4 reads an H5AD binary16 numeric scalar as a
Python `float` even though the stored datatype remains binary16. Its Zarr read
path cannot materialize the tested binary16 CSR matrix with the pinned SciPy;
the interoperability tests check the physical sparse components through Zarr
and verify native eager and backed reads. These limitations do not change the
on-disk dtype. Details, commands, and test coverage are in
[`tests/results/fp16.json`](../tests/results/fp16.json).
